# CAN Stop-Request Validation

가상 CAN 환경에서 저속 주행 정지 요청 기능의 메시지 이상 대응을 검증하는 학부 졸업논문 프로젝트입니다.

> 현재 상태: **기준선 v1.0, Python/CARLA 0.9.15 설치 완료, G0/G1/G2/G3 PASS**
> 실제 vCAN 요청 수신부터 CARLA 제동 적용과 차속 변화까지 확인했습니다. G4와 본시험은 아직 실행하지 않았습니다. 서버 종료 시 crash는 별도 미해결 항목입니다. 제출한 작성계획서는 수정하지 않았습니다.
> 2026-10-31: 사용자 장치 준비 후 G3 요청 프레임의 실제 송수신 PASS. 정상 5개와 정지 5개를 확인했습니다. 다음은 CARLA adapter이며 전체 G3는 아직 미실행입니다. [단계별 진행](docs/G3_PROGRESS.md)
> 2026-11-01: 전체 G3 첫 실제 실행 PASS. 정상 복원 뒤 제동 유지까지 확인했습니다. Codex가 구현 및 실행했고 사용자 검토와 직접 재현은 다음 단계입니다. [실제 연결 결과와 실행 안내](docs/G3_INTEGRATION.md)
>
> 시작 문서: [연구 및 시스템 기준선](docs/RESEARCH_BASELINE.md), [요구사항 및 시험 명세](docs/VALIDATION_PLAN.md), [논문 챕터별 구성](docs/THESIS_OUTLINE.md)

## 1. 연구 목적

CAN을 통해 전달되는 장애물 거리 정보가 중단되거나 과거 메시지가 반복될 때, 저속 주행 정지 요청 기능이 사전에 정의한 요구사항대로 대응하는지 시험합니다.

핵심은 새로운 자율주행 알고리즘 개발이 아니라 다음 검증 흐름을 구현하고 근거를 남기는 것입니다.

요구사항 정의 → 메시지 규격 정의 → 시험 시나리오 구성 → 이상 입력 재현 → 로그 수집 → 독립 판정 → 결과와 한계 분석

정상 입력에서 불필요한 정지 요청이 발생하지 않는지도 함께 확인합니다. 개선 방식이 무조건 우수하다고 가정하지 않고, 실패와 한계도 결과로 기록합니다.

### 논문 제목

**가상 CAN 환경에서 저속 주행 정지 요청 기능의 메시지 이상 대응 검증**

이미 제출한 작성계획서는 그대로 유지합니다. 사용자의 요청에 따라 구현과 시험의 기준을 v1.0 문서에 고정했습니다. CARLA 단독 실행은 G2, CAN 요청의 차량 적용은 G3에서 확인했습니다.

## 2. 확정한 설계와 남은 실행 확인

### 유지할 방향

- 차량 SW 검증과 평가를 중심에 둡니다.
- 실제 ECU 대신 역할이 분리된 소프트웨어 프로그램을 사용합니다.
- Linux SocketCAN의 가상 인터페이스인 vCAN을 사용합니다.
- 공개 구현을 근거로 최소 연결을 먼저 재현하고, 그 위에 논문 기능을 추가합니다.
- 실제 저장 로그와 시험 판정으로 성공 여부를 확인합니다.
- 회사 코드, 실제 차량의 비공개 DBC, 개인정보를 사용하지 않습니다.

### 실행 환경 기준과 미확인 상태

| 항목 | 첫 실행 기준 | 현재 상태 |
| --- | --- | --- |
| 운영체제 | Ubuntu 22.04 | Ubuntu 22.04.5, kernel 6.8.0-138 확인 |
| 통신 | Linux SocketCAN / vcan0 / Classic CAN | can-utils와 vcan0 UP 확인, 독립 송수신 G1 PASS |
| 언어 | Python | 프로젝트 .venv의 3.10.12 사용, 외부 Python 경로 배제를 위해 -I로 실행 |
| 시뮬레이터 | CARLA 0.9.15 | 서버/client 버전 일치 확인, Town04 단독 주행 및 제동 G2 PASS, 기존 0.9.14 client 제거 |
| Python 호환 환경 | 별도 프로젝트 venv | 격리 pip check 통과, 정확한 버전은 requirements.lock.txt |
| 메시지 해석 | python-can 4.6.1 / cantools 40.7.1 / 자체 DBC | Python 패키지 설치/import 완료, DBC 미구현 |
| 차량 연동 | CAN 수신 결과를 CARLA Python API에 적용 | G3 실제 CAN 수신, 제동 적용 및 실제 차속 PASS. 거리 판단 SUT 미구현 |
| 분석 | Python 기반 로그 판정과 표 및 그래프 | 미구현 |

CARLA 0.9.15를 첫 실행 기준으로 삼은 이유는 직접적인 공개 연동 사례가 이 버전을 고정해서 사용하기 때문입니다. 서버와 Python client 버전을 맞추고, 시스템 Python을 임의로 낮추지 않습니다. 버전 변경이 필요하면 호환성 근거와 기준선 개정 결정을 남깁니다.

2026-10-19에 최신 문서 확보와 G0를 수행했습니다. GPU는 RTX 4060 Laptop 8188 MiB, 드라이버 570.211.01입니다. 이후 실제 CARLA 프로세스의 NVIDIA GPU 사용과 G2 단독 제어를 확인했습니다. 최초 상태와 당시 설치 계획은 [G0 환경 점검](docs/G0_ENVIRONMENT_2026-10-19.md), 후속 실제 실행은 아래 기록으로 구분합니다. 본시험 성능은 아직 확인하지 않았습니다.

설치, G1/G2 결과와 실패 원인은 [SETUP_AND_SMOKE](docs/SETUP_AND_SMOKE_2026-10-19.md)에 기록합니다. 프로젝트 검사 명령은 `bash tools/check_project.sh`이며, 단위 검사는 실제 CARLA/vCAN 실행 판정과 구분합니다.

직접 실행할 때는 [검사 안내](docs/SELF_CHECK.md)를 따라 `bash tools/run_self_checks.sh check`, `g1`, `g2`, `g3-can`, `g3`을 사용합니다. `g3-can`은 요청 프레임만, `g3`은 실제 차량 연결까지 확인합니다. 새로 작성하거나 수정하는 코드 설명과 주석은 한글로 작성합니다.

ROS2는 이 최소 구성의 필수 의존성이 아닙니다. 이미 ROS2를 사용해 왔다는 이유만으로 ROS2 브리지나 전체 Autoware를 추가하지 않습니다.

### 설계 기준선 v1.0

메시지 ID와 byte 배치, 50 ms 송신, 200 ms 만료, 2 m 판단 임계값, 5 km/h 주행, 4개 시나리오별 A/B 10회씩 총 80회, 정지 잠금과 시간 및 판정 기준을 [설계 기준선](docs/RESEARCH_BASELINE.md)에 고정했습니다. 모두 연구용 설계값이며 양산 기준이나 실측 성능이 아닙니다.

거리 입력은 실제 센서 대신 사전 정의 수치 시퀀스로 생성합니다. CARLA는 차량 반응 확인에 사용하고 물리 장애물 충돌 회피는 주장하지 않습니다. 실제 설치 버전, spawn 좌표와 실행 성능은 Linux에서 확인하고 기록해야 합니다. 기준선 변경이 필요하면 근거와 사용자 결정을 남기며, 결과를 맞추기 위해 합격 기준을 사후 조정하지 않습니다.

## 3. 시스템 구조

| 구성 | 역할 |
| --- | --- |
| Input publisher | 장애물 거리 정보와 필요한 정상 상태 정보를 주기적으로 CAN 송신 |
| Fault injector / scenario runner | 대상 거리 메시지의 송신 중단 또는 동일 순번 프레임 반복을 제어 |
| Stop-request controller (SUT) | 입력의 유효성과 갱신 상태를 판단하고 정지 요청 생성 |
| Request sink / CARLA adapter | 정지 요청을 수신하고 적용 결과를 기록, 시뮬레이터 제어에 연결 |
| Independent logger / test oracle | 입력과 요청 및 차량 상태를 기록해 요구사항별 기대 결과와 비교 |

SUT는 System Under Test, 즉 검증 대상 프로그램입니다. 이 프로그램들을 실제 ECU 펌웨어나 실제 브레이크 ECU로 표현하지 않습니다.

모든 프로그램은 같은 가상 CAN 버스를 공유할 수 있습니다. CAN ID는 메시지를 구별하는 식별자이며, ECU에 데이터를 개별 배달하는 목적지 주소처럼 설명하지 않습니다.

수신 프로그램의 로그는 응용 프로그램 수준의 수신 확인입니다. 물리 CAN의 ACK 또는 실제 차량 정지 성공을 뜻하지 않습니다. v1.0은 별도의 응답 CAN 메시지를 정의하지 않습니다.

## 4. 본시험 4개

| 시험 | 입력 변화 | 검증 목적 |
| --- | --- | --- |
| 정상 근거리 진입 | 정상적으로 갱신되는 수치 입력이 정지 판단 조건에 진입 | 정상 조건에서 필요한 정지 요청 발생 |
| 정상 비정지 조건 | 충분한 거리와 정상 갱신 유지 | 불필요한 정지 요청 방지 |
| 거리 메시지 수신 중단 | 해당 메시지만 송신 중단 | 마지막 정보를 계속 신뢰하지 않고 정의한 대응 수행 |
| 과거 메시지 반복 | 같은 순번과 payload의 프레임을 계속 송신 | 수신 중이라는 이유만으로 신규 정보로 오판하지 않음 |

정상 원거리, 정상 근거리 진입, 거리 메시지 중단, 과거 프레임 반복으로 고정합니다. 정상 비정지 조건은 음성 대조 조건입니다. 이상 입력은 5~8초 구간에 주고 복원 뒤에도 정지 잠금을 확인합니다. 지연, invalid, 범위 초과와 자동 재출발을 별도 본시험으로 추가하지 않습니다.

비교는 수신 도착만 보는 A와, 수신 타임아웃에 순번 갱신 감시를 추가한 B입니다. 사전에 고정한 공통 요구사항으로 판정하고 기본 방식의 미충족도 결과로 남깁니다.

상세 내용은 [검증 계획](docs/VALIDATION_PLAN.md)을 확인하세요.

## 6. Linux Codex가 가장 먼저 해야 할 일

**논문 전체 구현보다 최소 연결 검증이 먼저입니다.**

1. G0 환경 점검 기록을 읽고, 이후 변경된 환경이 있는지 확인합니다. 최초 점검은 2026-10-19 완료했습니다.
2. 필요한 도구와 프로젝트 환경을 준비한 뒤 독립 프로그램 사이의 vCAN 송수신을 확인합니다.
3. CARLA를 단독 실행하고 차량 제어 및 실제 차속 조회를 확인합니다.
4. CAN으로 수신한 제어 명령을 CARLA 차량에 적용하고 차속 변화를 기록합니다.
5. 거리 메시지 중단부터 정지 요청 발생, 수신, 차량 제어 적용까지 최소 시험 하나를 연결합니다.

단계별 명령, 버전, 로그, 성공 또는 실패를 기록합니다. 설치만 성공했거나 candump에 프레임이 보였다는 이유로 전체 검증을 완료 처리하지 않습니다.

실행 절차와 첫 프롬프트는 [Linux 인수인계](docs/LINUX_HANDOFF.md)를 확인하세요.

## 7. 연구 범위의 한계

- vCAN으로 실제 배선 고장, 전기적 오류, bus-off, 물리 CAN의 ACK나 실제 버스 중재 성능을 검증하지 않습니다.
- 거리 정보 수신 중단은 해당 인터페이스에서 보이는 현상을 재현하는 것입니다. 초음파센서의 물리 고장 원인을 특정한 결과가 아닙니다.
- 사전 정의 거리 수치는 실제 초음파의 반사, 간섭, 재질별 오차 또는 CARLA 물체까지의 실제 거리를 검증한 것이 아닙니다.
- 정지 요청의 발생, CAN 전달, 제어 적용, 실제 차속 감소는 별도의 검증 단계입니다.
- 시뮬레이션 결과를 양산차 안전성 인증이나 실차 제동 성능 입증으로 확대하지 않습니다.
- 수신 순번이 증가한다는 사실만으로 센서 측정 시각 자체의 최신성이 보장되지는 않습니다.

- 현재 단계: G3 실제 CAN/CARLA 통합 PASS. 다음은 사용자 검토와 직접 재현, 이후 G4 최소 거리 판단 연결
- 실제 실행 결과: G1 PASS, G2는 실패 2건 보존 후 PASS 2건, G3 요청 전달과 실제 차량 연결 PASS. A/B 제어기와 G4 및 본시험 결과는 없음
- 남은 환경 문제: Ctrl+C 서버 종료에서 Signal 11/exit 139를 3회 관측. 차량 정리와 설정 복구 이후 발생했으며 원인은 미해결
