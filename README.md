# CAN Stop-Request Validation

가상 CAN 환경에서 저속 주행 정지 요청 기능의 메시지 이상 대응을 검증하는 학부 졸업논문 프로젝트입니다.

> 현재 상태: **문서 기반 프로젝트 준비 완료 / 구현 및 Linux 실행 검증 미완료**
> 이 저장소에는 연구 계획과 Codex 인수인계 문서만 있습니다. 아직 실행 가능한 논문 시스템이나 실험 결과는 없습니다.

## 1. 연구 목적

CAN을 통해 전달되는 장애물 거리 정보가 중단되거나 과거 메시지가 반복될 때, 저속 주행 정지 요청 기능이 사전에 정의한 요구사항대로 대응하는지 시험합니다.

핵심은 새로운 자율주행 알고리즘 개발이 아니라 다음 검증 흐름을 구현하고 근거를 남기는 것입니다.

요구사항 정의 → 메시지 규격 정의 → 시험 시나리오 구성 → 이상 입력 재현 → 로그 수집 → 독립 판정 → 결과와 한계 분석

정상 입력에서 불필요한 정지 요청이 발생하지 않는지도 함께 확인합니다. 개선 방식이 무조건 우수하다고 가정하지 않고, 실패와 한계도 결과로 기록합니다.

### 잠정 논문 제목

**가상 CAN 환경에서 저속 주행 정지 요청 기능의 메시지 이상 대응 검증**

제목과 구체적인 연구방법은 지도교수 검토 및 최소 실행 검증을 거쳐 확정합니다. CARLA 사용은 첫 재현 후보이며, 아직 우리 환경에서 실행 가능성이 확인된 것은 아닙니다.

## 2. 지금까지 결정한 방향과 아직 결정하지 않은 사항

### 유지할 방향

- 차량 SW 검증과 평가를 중심에 둡니다.
- 실제 ECU 대신 역할이 분리된 소프트웨어 프로그램을 사용합니다.
- Linux SocketCAN의 가상 인터페이스인 vCAN을 사용합니다.
- 공개 구현을 근거로 최소 연결을 먼저 재현하고, 그 위에 논문 기능을 추가합니다.
- 실제 저장 로그와 시험 판정으로 성공 여부를 확인합니다.
- 회사 코드, 실제 차량의 비공개 DBC, 개인정보를 사용하지 않습니다.

### 잠정 구현 후보

| 항목 | 첫 재현 후보 | 현재 상태 |
| --- | --- | --- |
| 운영체제 | Ubuntu 22.04 | 사용자 보유, 이번 프로젝트 실행 미확인 |
| 통신 | Linux SocketCAN / vcan0 / Classic CAN | 미실행 |
| 언어 | Python | 버전 설치 상태 미확인 |
| 시뮬레이터 | CARLA 0.9.15 | 미설치 또는 설치 여부 미확인 |
| 참고 구현의 Python 환경 | Python 3.9 별도 환경 | 우리 환경에서 재현하지 않음 |
| 메시지 해석 | python-can / cantools / 자체 DBC | 후보, 설치 미확인 |
| 차량 연동 | CAN 수신 결과를 CARLA Python API에 적용 | 공개 코드 확인, 우리 환경 미실행 |
| 분석 | Python 기반 로그 판정과 표 및 그래프 | 미구현 |

CARLA 0.9.15를 먼저 제안한 이유는 직접적인 공개 연동 사례가 이 버전을 고정해서 사용하기 때문입니다. 서버와 Python client 버전을 맞추고, 시스템 Python을 임의로 낮추지 않습니다. 0.9.16이나 다른 버전은 별도의 호환성 검증 후 선택합니다.

ROS2는 이 최소 구성의 필수 의존성이 아닙니다. 이미 ROS2를 사용해 왔다는 이유만으로 ROS2 브리지나 전체 Autoware를 추가하지 않습니다.

### 아직 확정하지 않은 사항

메시지 ID와 신호 배치, 송신 주기, 타임아웃, 정지 판단 거리, 초기 속도, 반복 시험 횟수, 합격 허용 시간, 복구 및 재개 정책, 거리 입력 생성 방법, 시간 기준의 최종 운용 방식은 아직 확정하지 않았습니다.

이 저장소의 제안이나 TODO를 사용자가 승인한 요구사항 또는 양산차 안전 기준처럼 취급하지 않습니다.

## 3. 제안 시스템 구조

| 구성 | 역할 |
| --- | --- |
| Input publisher | 장애물 거리 정보와 필요한 정상 상태 정보를 주기적으로 CAN 송신 |
| Fault injector / scenario runner | 대상 거리 메시지의 송신 중단 또는 동일 순번 프레임 반복을 제어 |
| Stop-request controller (SUT) | 입력의 유효성과 갱신 상태를 판단하고 정지 요청 생성 |
| Request sink / CARLA adapter | 정지 요청을 수신하고 적용 결과를 기록, 시뮬레이터 제어에 연결 |
| Independent logger / test oracle | 입력과 요청 및 차량 상태를 기록해 요구사항별 기대 결과와 비교 |

SUT는 System Under Test, 즉 검증 대상 프로그램입니다. 이 프로그램들을 실제 ECU 펌웨어나 실제 브레이크 ECU로 표현하지 않습니다.

모든 프로그램은 같은 가상 CAN 버스를 공유할 수 있습니다. CAN ID는 메시지를 구별하는 식별자이며, ECU에 데이터를 개별 배달하는 목적지 주소처럼 설명하지 않습니다.

수신 프로그램의 응답 메시지는 응용 프로그램 수준의 확인입니다. 물리 CAN의 ACK 또는 실제 차량 정지 성공을 뜻하지 않습니다.

## 4. 핵심 시험 후보

| 시험 | 입력 변화 | 검증 목적 |
| --- | --- | --- |
| 정상 장애물 접근 | 정상적으로 갱신되는 거리 정보가 정지 판단 조건에 진입 | 정상 조건에서 필요한 정지 요청 발생 |
| 정상 비정지 조건 | 충분한 거리와 정상 갱신 유지 | 불필요한 정지 요청 방지 |
| 거리 메시지 수신 중단 | 해당 메시지만 송신 중단 | 마지막 정보를 계속 신뢰하지 않고 정의한 대응 수행 |
| 과거 메시지 반복 | 같은 순번과 payload의 프레임을 계속 송신 | 수신 중이라는 이유만으로 신규 정보로 오판하지 않음 |

정상 입력, 수신 중단, 과거 메시지 반복의 세 범주를 우선합니다. 정상 비정지 조건은 음성 대조 조건입니다. 지연, invalid, 범위 초과, 복구 시험 등은 요구사항과 일정 검토 후 추가할 후보이며 모두 구현하기로 확정한 것이 아닙니다.

비교 후보는 수신 도착만 보는 기본 타임아웃 방식과, 수신 타임아웃에 메시지 갱신 순번 검사를 추가한 방식입니다. 구체적인 규칙과 수치는 실행 근거를 확보한 뒤 정의합니다.

상세 내용은 [검증 계획](docs/VALIDATION_PLAN.md)을 확인하세요.

## 5. 구현 근거로 조사한 공개 코드

조사일: 2026-10-13. 아래는 소스 확인 결과이지, 우리 노트북에서 실행한 결과가 아닙니다.

### Yes, CARLA CAN

- [저장소와 확인한 CAN 중심 버전](https://github.com/luigiluz/yes-carla-can/tree/eee3c5224ab2941edb08dfa8f4a4f735e7f981d6)
- 작성자 README에 Ubuntu 22.04와 Python 3.9 환경을 명시합니다.
- requirements는 CARLA 0.9.15, python-can 4.6.1, cantools 40.7.1을 사용합니다.
- 실제 코드에 SocketCAN 수신, DBC 해석, CARLA VehicleControl 적용 경로가 있습니다.
- 기존 레이더 메시지는 검출 이벤트 기반입니다. 주기적 거리 정보의 freshness 검증을 그대로 제공하지 않습니다.
- 기존 수신 코드에 우리가 원하는 타임아웃 정지와 거리 메시지 순번 검사는 없습니다.
- 최신 main에는 추가 네트워크 구성이 있어, 처음부터 전체 설치 스크립트를 실행하지 않습니다.
- 공개 테스트는 CARLA와 CAN 버스를 mock으로 대체합니다. 이를 실제 차량 연동 성공으로 해석하지 않습니다.

### Autoware Safety Island CAN-CARLA bridge

- [확인한 bridge 디렉터리](https://github.com/autowarefoundation/autoware-safety-island/tree/243af978c47f1020295b1a03e722cc4604b759da/demo/can_carla_bridge)
- SocketCAN 수신을 CARLA Ackermann 제어에 연결하는 실제 코드가 있습니다.
- 제어명령 순번 검사와 watchdog 및 실제 vCAN 왕복 테스트 코드가 있습니다.
- 거리 입력 메시지의 정지 판단을 완성한 예제는 아닙니다.
- CI에서는 CARLA를 실행하지 않습니다. 전체 Autoware나 RTOS 스택을 가져오는 계획도 아닙니다.

### python-can

- [확인한 SocketCAN 주기 송신 테스트](https://github.com/hardbyte/python-can/blob/b4f82abede25ff83376be793a2935c41f81c3869/test/test_cyclic_socketcan.py)
- 실제 vcan0 송수신, 주기 송신 중단, 같은 프레임 반복 등에 대한 구현 참고 근거가 있습니다.
- 라이브러리 최신 버전을 앞선 저장소의 고정 환경과 무조건 혼합하지 않습니다.

구체적인 파일과 한계는 [소스 조사 기록](docs/SOURCE_AUDIT.md)에 정리했습니다. 외부 코드를 복사하거나 수정할 경우 원본 저작권 표시와 라이선스를 보존하고, 논문에서도 참고한 구현과 직접 구현한 부분을 구분합니다.

## 6. Linux Codex가 가장 먼저 해야 할 일

**논문 전체 구현보다 최소 연결 검증이 먼저입니다.**

1. Ubuntu와 GPU 및 Python의 현재 환경을 읽기 전용으로 점검하고 기록합니다.
2. 독립 프로그램 사이의 vCAN 송수신을 확인합니다.
3. CARLA를 단독 실행하고 차량 제어 및 실제 차속 조회를 확인합니다.
4. CAN으로 수신한 제어 명령을 CARLA 차량에 적용하고 차속 변화를 기록합니다.
5. 거리 메시지 중단부터 정지 요청 발생, 수신, 차량 제어 적용까지 최소 시험 하나를 연결합니다.

단계별 명령, 버전, 로그, 성공 또는 실패를 기록합니다. 설치만 성공했거나 candump에 프레임이 보였다는 이유로 전체 검증을 완료 처리하지 않습니다.

실행 절차와 첫 프롬프트는 [Linux 인수인계](docs/LINUX_HANDOFF.md)를 확인하세요.

## 7. 연구 범위의 한계

- vCAN으로 실제 배선 고장, 전기적 오류, bus-off, 물리 CAN의 ACK나 실제 버스 중재 성능을 검증하지 않습니다.
- 거리 정보 수신 중단은 해당 인터페이스에서 보이는 현상을 재현하는 것입니다. 초음파센서의 물리 고장 원인을 특정한 결과가 아닙니다.
- CARLA 거리 입력을 사용해도 실제 초음파의 반사, 간섭, 재질별 오차를 검증한 것이 아닙니다.
- 정지 요청의 발생, CAN 전달, 제어 적용, 실제 차속 감소는 별도의 검증 단계입니다.
- 시뮬레이션 결과를 양산차 안전성 인증이나 실차 제동 성능 입증으로 확대하지 않습니다.
- 수신 순번이 증가한다는 사실만으로 센서 측정 시각 자체의 최신성이 보장되지는 않습니다.
