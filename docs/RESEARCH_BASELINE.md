# 연구 및 시스템 설계 기준선 v1.0

작성일: 2026-10-16

상태: **IMPLEMENTATION_BASELINE / NOT_EXECUTED**

사용자의 "계획서는 수정하지 않고 구현을 위한 문서 최종안을 정한다"는 요청에 따라 연구 범위와 설계 선택을 고정한다. 제출한 작성계획서와 HWP 원본은 변경하지 않는다. 아래 수치는 이 학부 연구의 자체 설계 기준이며, 양산차 요구사항, 법규, 표준 권고값, 교수의 개별 승인 또는 이미 확인한 성능을 뜻하지 않는다. 문서 확정과 구현 및 실험 완료는 별개다.

## 1. 제목과 연구 질문

제목: **가상 CAN 환경에서 저속 주행 정지 요청 기능의 메시지 이상 대응 검증**

연구 질문: 정상 입력, 거리 메시지 수신 중단, 동일한 과거 프레임 반복 조건에서 수신 타임아웃만 감시하는 방식과 메시지 순번의 갱신도 감시하는 방식은 어떤 요구사항을 충족하거나 충족하지 못하는가?

기여는 새로운 제어 알고리즘이 아니라, 요구사항에서 시험과 증거 및 판정까지 추적할 수 있는 소규모 검증 체계다. 과거 프레임 반복에 대한 기본 방식의 관측 한계는 설계상 예상할 수 있다. 이를 새로운 발견이나 모든 센서 고장에 대한 해결책으로 포장하지 않는다.

## 2. 포함 범위와 제외 범위

포함한다.

- Linux SocketCAN의 실제 vcan0 인터페이스를 통한 독립 프로그램 간 프레임 송수신.
- 정상 원거리, 정상 근거리 진입, 거리 메시지 중단, 과거 프레임 반복의 4개 본시험.
- 두 방식의 정지 요청, 요청 수신과 제어 호출, CARLA 차량 속도의 분리 검증.
- 입력이 복원돼도 정지 요청을 유지하는 잠금 정책과 시험 간 수동 초기화.
- 고정된 입력, 원시 로그, 독립 판정 프로그램과 표 및 그래프 생성.

제외한다.

- 실물 ECU 펌웨어, 실제 CAN 배선과 ACK, 전기적 오류, bus-off, 물리 버스 중재 성능.
- 카메라, 레이더, 초음파 센서 모델과 실제 센서의 고장 원인 진단.
- 물리 장애물과의 충돌 회피, 정지 거리의 안전성, 자율주행 경로 계획과 신규 제어기 비교.
- 지연, invalid, 범위 초과 등의 별도 본시험 추가와 자동 재출발 성능 비교.
- ROS2, Autoware 전체 구성, RTOS, CAN-FD, 공격 및 침입 탐지 기능.
- 기능안전 인증 또는 실차 제동 성능의 입증.

## 3. 거리 입력과 CARLA의 역할

거리 입력은 시험 실행자가 사전에 정한 수치 시퀀스로 생성한다. 실제 센서나 CARLA 장애물에서 측정한 거리가 아니다. 단위는 cm이며, 정상 유효 범위는 0~10,000 cm다.

선택 이유는 메시지 이상 이외의 인지 오차와 센서 모델 차이를 배제하고, CARLA 유무와 관계없이 동일한 입력을 재현하기 위해서다. 거리 수치가 CARLA 차량과 특정 물체 사이의 실제 기하 거리에 대응한다고 주장하지 않는다.

CARLA는 저속 모사 차량에 정지 요청을 연결하고 시뮬레이터 상태에서 감속과 정지를 확인하는 용도다. 본 연구의 2 m는 수치 입력에 대한 판단 임계값이지, 장애물 앞 안전 정지를 보장하는 안전거리 기준이 아니다.

## 4. 구성 요소

| 구성 | 역할 | 확인 근거 |
| --- | --- | --- |
| Sensor stub | 정해진 거리와 순번, 배경 심박 송신 | 전송한 ID, payload와 송신 시각 |
| Stop-request controller | A 또는 B 하나를 실행 | 입력 해석과 정지 요청 CAN 출력 |
| Brake adapter | 요청 수신 후 CARLA 제어 호출 | 수신, 호출 완료, 이후 차량 상태 |
| Scenario runner | 실행 순서, 이상 주입, 시작과 종료 관리 | 사전 입력과 실제 실행의 일치 |
| Independent observer / oracle | 별도 CAN 수신과 로그 기반 판정 | SUT 스스로 선언한 PASS가 아닌 외부 증거 |

앞의 세 프로그램은 ECU의 일부 역할을 흉내 낸다. 실제 ECU나 브레이크 펌웨어가 아니다. A와 B는 서로 분리된 run으로 비교한다. SUT는 System Under Test, 즉 검증 대상 프로그램이다.

## 5. 고정 설계값과 선택 이유

| 항목 | 기준선 값 | 선택 이유 |
| --- | --- | --- |
| 거리 및 배경 프레임 주기 | 50 ms, 20 Hz | 저부하에서 여러 갱신을 관찰 |
| 제어기 검사 주기 | 10 ms | 50 ms 입력 사이에서 만료 검사 |
| 수신 및 순번 갱신 타임아웃 | 200 ms | 명목 주기의 4배인 연구용 기준 |
| 근거리 정지 조건 | 유효 거리 <= 200 cm | 거리 조건과 통신 이상을 분리 |
| 정지 요청 송신 | 상태 전이 즉시, 이후 50 ms마다 | 최초 대응과 유지 상태 관찰 |
| 근거리 요청 관찰 상한 | 기준 프레임 송신 완료 후 100 ms | 독립 관찰자 기준 종단 소프트웨어 한도 |
| 메시지 이상 요청 관찰 상한 | 마지막 신규 프레임 송신 완료 후 300 ms | 200 ms 만료에 관찰 여유 100 ms |
| adapter 처리 한도 | 요청 수신 후 50 ms 이내 제어 호출 완료 | 요청과 호출을 분리 평가 |
| 목표 속도 | 5 km/h, 약 1.389 m/s | 저속 정지 반응으로 범위 제한 |
| 시작 속도 | 5.0 +/- 0.5 km/h를 1.0 s 이상 유지 | 공통 이동 상태 확보 |
| CARLA 시간 간격 | 0.05 s, 동기 모드 | 일정한 시뮬레이션 관찰 간격 |
| 정지 판정 | 평면 속도 <= 0.1 m/s를 연속 0.5 s 유지 | 단일 저속 표본의 오판 방지 |
| 정지 관찰 창 | 최초 제동 적용 frame부터 2.0 s의 시뮬레이션 시간 | 0.5 s 유지까지 이 창 안에 완료 |
| 입력 구간 길이 | run 시작 후 호스트 시간 20 s | 근거리 진입 및 이상 후 복원 관찰 |
| 본시험 반복 | 4개 시나리오 x 2개 방식 x 10회 = 80회 | 같은 설정의 반복성 확인 |

이 값들은 실행 가능성이 입증됐다는 뜻이 아니다. 환경이 충족하지 못하면 실패 또는 미실행을 기록한다. 결과를 본 뒤 숫자를 완화해서 PASS로 바꾸지 않는다. 변경이 꼭 필요하면 사용자와 이유를 확인하고 v1.1 이상으로 개정한 뒤 영향받는 시험을 다시 수행한다.

## 6. 메시지 계약

Classic CAN, 표준 11-bit ID, DLC 8, little-endian을 사용한다. 아래 ID는 연구용 자체 할당이며 실제 차량 DBC가 아니다. 확장 ID, RTR, 오류 프레임은 정상 입력으로 사용하지 않는다.

| ID | 이름 | byte 배치 | 송신 |
| --- | --- | --- | --- |
| 0x100 | DistanceInput | 0~1: uint16 distance_cm, 2: uint8 counter, 3: uint8 valid, 4~7: uint32 run_token | 50 ms |
| 0x101 | BackgroundHeartbeat | 0: uint8 counter, 1~3: 0, 4~7: uint32 run_token | 50 ms, 거리 이상 중에도 계속 |
| 0x200 | StopRequest | 0: uint8 stop, 1: uint8 reason, 2: uint8 counter, 3: 0, 4~7: uint32 run_token | 전이 즉시 및 50 ms |

- valid=1인 거리 프레임만 인정한다. 다른 ID, 잘못된 길이, 현재 run과 다른 token, 디코딩 실패, 범위 밖 거리, valid!=1은 입력 값을 갱신하지 않는다.
- 본시험에는 invalid 조건을 추가하지 않고 디코더 단위 점검에서만 확인한다.
- run_token은 실행 간 오래된 프레임 혼입을 구분하는 식별값이지 보안 인증이 아니다. 전체 run_id와의 대응을 metadata에 저장한다.
- reason: 0=NORMAL, 1=NEAR_DISTANCE, 2=RX_TIMEOUT, 3=NO_SEQUENCE_PROGRESS, 4=INIT_INHIBITED.
- 정지 시 최초 원인을 잠금 해제 전까지 유지한다. 동시에 충족되면 RX_TIMEOUT, NO_SEQUENCE_PROGRESS, NEAR_DISTANCE 순으로 기록한다.
- adapter 로그는 응용 프로그램 수준의 수신과 호출 증거다. 물리 CAN ACK를 측정하지 않는다.

## 7. 두 방식의 정의와 상태 전이

### 공통

거리 <= 200 cm이면 정지 요청을 발생시킨다. 요청은 해당 run 종료까지 잠근다. 거리가 멀어지거나 입력이 복원돼도 자동으로 해제하지 않는다.

기동 시 INIT_INHIBITED 상태로 정지를 유지한다. 시험 실행자는 정상 입력 5개 이상, 프로그램 준비와 올바른 token을 확인한 뒤 명시적으로 arm한다. 이동 안정화 후 본시험 시간 구간을 시작한다. 기동과 준비를 30 s 안에 마치지 못하면 원인을 기록하고 해당 시도를 종료한다. 입력이 없는 상태에서 무기한 대기하며 차량을 이동시키지 않는다.

### A: 수신 타임아웃

올바른 거리 프레임마다 last_valid_rx와 사용할 거리 값을 갱신한다. 동일 순번 여부는 판단하지 않는다. now-last_valid_rx >= 200 ms이면 정지한다. 배경 프레임은 이 시각을 갱신하지 않는다.

### B: 수신 타임아웃 + 순번 갱신 감시

A의 수신 타임아웃에 더해 last_progress_rx를 관리한다. 마지막으로 인정한 순번에 대해 delta=(new_counter-last_counter) mod 256을 계산한다.

- 첫 유효 프레임: 순번과 갱신 시각을 초기화.
- delta 1~127: 전진으로 인정하고 거리, 마지막 인정 순번과 갱신 시각을 변경.
- delta 0: 반복으로 분류하고 위 세 값을 변경하지 않음.
- delta 128~255: 허용 전진 범위 밖으로 분류하고 위 세 값을 변경하지 않음.

유효 프레임의 도착은 수신 시각에 기록하되, 거절된 순번은 신규 정보의 근거로 쓰지 않는다. now-last_progress_rx >= 200 ms이면 정지한다. 255->0은 delta=1이다. 이 규칙은 모든 순번 재생을 검출하지 않으며, 오래된 측정값에 송신자가 새 순번을 붙이는 고장은 대상 밖이다.

## 8. 차량과 시간 운용

- CARLA 0.9.15와 일치하는 Python client를 첫 실행 기준으로 사용한다. 설치와 호환성은 실제 확인한다.
- Town04의 평탄한 직선 구간, vehicle.tesla.model3, ClearNoon, 다른 차량과 보행자 없음으로 구성한다. 정지하지 않는 run도 구간 끝이나 장애물에 닿지 않도록 최소 100 m 구간을 준비한다. 실제 spawn 좌표와 물리 설정은 본시험 전에 기록하고 A/B 전체에 고정한다. 실행 환경에서 기록할 정보이지 결과를 보고 고르는 조건이 아니다.
- 정상 이동에는 CARLA 내장 Ackermann 속도 제어를 사용한다. 새 제어 알고리즘을 연구하지 않는다. 요청 뒤에는 adapter 한 곳에서 throttle=0, brake=1, steer=0, hand_brake=False를 적용하고 유지한다. autopilot과 키보드 제어는 끈다.
- 요청 없는 주행이 임의로 멈추거나 구간을 이탈하면 성공으로 보지 않고 원인을 기록한다.
- CAN과 요청의 시각 비교에는 같은 호스트의 time.monotonic_ns()만 쓴다. 달력 시각이나 CARLA 시간과 직접 빼지 않는다.
- CARLA는 단일 coordinator만 tick한다. 0.05 s 시뮬레이션 간격과 별개로 호스트상 50 ms 간격 실행을 목표로 하고 지연을 기록한다. 고정 시간 간격이 실시간 실행을 보장하지는 않는다.
- 제어 호출 완료는 호스트 시각으로 기록한다. 다음 tick 이후 최초 제동 적용을 확인한 CARLA frame과 시뮬레이션 시각을 따로 남긴다. 운동 판정의 2.0 s는 후자를 기준으로 한다.
- 차량 평면 속도는 get_velocity()의 sqrt(vx^2+vy^2)로 계산한다. 목표 속도나 정지 요청으로 대체하지 않는다.

## 9. 산출물과 실행 순서

산출물은 자체 DBC, 두 방식의 프로그램, 고정 입력, 독립 로그, 추적표, 자동 판정 결과, 그래프, 환경 기록과 논문이다. 아직 구현되거나 결과가 확보된 것은 아니다.

Linux에서는 G0 환경 확인, G1 독립 vCAN 송수신, G2 CARLA 단독 제어, G3 CAN 명령의 차량 적용, G4 최소 이상 대응 연결을 먼저 수행한다. 이후 단위 점검, CARLA 없는 메시지 수준 예비 시험, 80회 본시험 순으로 진행한다.

## 10. 기술 근거

공식 문서는 인터페이스와 API의 근거이며 이 연구의 수치를 제공하는 안전 기준 문서가 아니다.

- [Linux SocketCAN 및 vCAN](https://docs.kernel.org/networking/can.html#the-virtual-can-driver-vcan): 물리 제어기 없이 로컬 CAN 프레임 송수신.
- [CARLA 0.9.15 동기와 시간 간격](https://carla.readthedocs.io/en/0.9.15/adv_synchrony_timestep/): 고정 간격과 단일 tick 소유자.
- [CARLA 0.9.15 Python API](https://carla.readthedocs.io/en/0.9.15/python_api/): Ackermann 제어, VehicleControl, get_velocity. 호출과 다음 tick 적용을 구분한다.
