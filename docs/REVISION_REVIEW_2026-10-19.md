## 3. 이전 분석에서 달라진 판단

이전에는 설계값과 복구 정책이 미정인 문서 준비 단계였다. 최신 상태는 **DESIGN_BASELINED / IMPLEMENTATION_NOT_STARTED**다. 구현 기준선 v1.0을 사용자가 받아들여 게시한 사실이 기록되어 있다. 제출한 작성계획서는 수정하지 않는다.

| 항목 | 최신 v1.0에서 고정한 내용 |
| --- | --- |
| 입력 출처 | 실제 센서 대신 사전 정의 거리 수치 시퀀스 |
| CARLA 역할 | 요청에 따른 제어 적용과 실제 시뮬레이터 속도 관찰 |
| 메시지 | 표준 Classic CAN, DLC 8, little-endian, 거리 0x100 / 심박 0x101 / 요청 0x200 |
| 입력 및 감시 | 50 ms 입력, 10 ms 검사, 200 ms 만료 |
| 거리 및 주행 | 거리 조건 <= 200 cm, 목표 5 km/h |
| 비교 | A는 유효 거리 수신 타임아웃, B는 동일 감시에 순번 진전 감시 추가 |
| 반복 판정 | 마지막 신규 프레임 기준으로 외부 요청 관찰 기한 적용 |
| 복구 | 정지 잠금 유지, run 사이 수동 초기화, 자동 재출발 없음 |
| 시간 | 메시지는 호스트 monotonic, 운동 판정은 CARLA 시뮬레이션 시간 |
| 본시험 | 4개 시나리오 x A/B x 10번의 원래 시도 = 80회 계획 |
| 실패 처리 | 실패와 오류 보존, 추가 실행 별도 집계, PASS가 나올 때까지 반복하지 않음 |

이 항목들을 다시 미정으로 취급하거나 임의로 재선정하지 않는다. 실행상 기준선 변경이 필요하면 근거와 사용자 결정을 남기고 버전을 올리는 절차를 따른다. 문서의 값은 연구용 설계값이며 교수의 개별 승인이나 측정 성능을 뜻하지 않는다.

## 4. 연구와 논문으로 이해한 흐름

거리 fixture를 송신하고, 시나리오에 따라 0x100만 중단하거나 같은 payload를 반복한다. A 또는 B가 0x200을 송신한다. adapter가 이를 받아 제동 호출을 수행하고, CARLA의 실제 제어 상태와 속도로 반응을 확인한다. 별도 observer와 판정기가 입력, 요청, 적용과 운동을 요구사항별로 평가한다.

본시험은 정상 원거리 T-01, 정상 근거리 진입 T-02, 거리 메시지 중단 T-03, 과거 프레임 반복 T-04다. T-03과 T-04는 계속 1000 cm를 사용하므로 근거리 조건으로 먼저 멈추는 현상과 통신 이상 대응을 분리한다. 두 경우 모두 배경 심박은 유지한다.

논문의 기여는 요구사항에서 독립 증거와 판정까지 추적할 수 있는 검증 체계다. 반복 프레임에 대한 A의 한계는 설계상 예상할 수 있으므로 새로운 발견으로 주장하지 않는다. 기대 동작과 실측 결과를 분리한 점, 정상 비정지 조건과 실패 보존을 포함한 점이 비교의 해석을 분명하게 한다.

논문은 서론, 관련 기술 및 참고 구현, 요구사항과 시스템 설계, 시험 방법, 결과 분석, 결론의 6장으로 연결된다. 결과와 결론의 효과 및 수치는 실제 시험 뒤에 작성한다. 현재 구현, 예비 결과와 본시험 결과는 없다.

## 5. 시간과 관측 기준의 이해

- 근거리 요청은 최초 유효 근거리 프레임 송신 완료 후 100 ms 안에 독립 observer에서 관찰되어야 한다.
- 중단과 반복은 마지막 신규 프레임의 송신 시작+200 ms 이후, 송신 완료+300 ms 이내에 요청이 관찰되어야 한다.
- adapter 제동 호출 완료는 해당 요청 수신 후 50 ms 이내다.
- 차량 정지는 최초 제동 적용 확인 frame부터 2.0 s의 시뮬레이션 시간 안에 속도 <= 0.1 m/s를 연속 0.5 s 이상 확보하는 기준이다.
- 제어기 내부 시각만으로 합격을 선언하지 않으며, 호스트 시간과 CARLA 시간을 직접 빼지 않는다.

명세의 산술을 확인했다. T-02는 n=260, 명목 13.0 s에 200 cm에 도달한다. 이상 시험의 마지막 신규 프레임은 n=99, 명목 4.95 s이고 명목 만료는 5.15 s다. 이상 슬롯은 60개, 복원 순번 차이는 61이다. 0.05 s 간격으로 0.5 s를 포괄하려면 통상 11개 표본이 필요하다. 실제 판정은 명목 시각 대신 기록한 실제 송신 경계를 사용한다.

## 6. 구현 시 해석을 맞춰야 할 두 경계

네 본시험의 고정 수치 사이에서 명백한 산술 모순은 발견하지 못했다. 다음은 수치나 정책의 재선정 사항이 아니라 코드와 판정기의 관측 범위를 맞추기 위한 주의점이다.

1. **준비 구간과 본시험의 최초 요청.** 기동 중 INIT_INHIBITED는 stop=1을 보낸다. q_obs와 최초 제동 적용 frame을 구할 때 이 준비 상태를 본시험 사건과 구분해야 한다. 준비 로그를 보존하면서 t0 이후의 본시험 사건을 판정해야 불필요 요청이나 운동 창을 잘못 계산하지 않는다. 근거: 기준선 7절, 시험 명세 2절 및 4절.
2. **요청 관찰과 adapter 수신의 대응.** StopRequest에는 counter가 있지만 증가와 초기화 규칙은 상세히 적혀 있지 않다. 전이 직후 요청과 주기 재송신을 구분하고, observer와 adapter가 관측한 요청을 일관되게 대응시킬 필요가 있다. 뒤늦은 재송신을 골라 최초 요청 처리 실패를 가리지 않아야 한다. 근거: 기준선 5~6절, 시험 명세 관찰 시각 정의.

실제 구현 버그가 발견됐다는 의미는 아니다. 아직 코드가 없으며, 이 분석에서는 기준선을 변경하지 않았다.
